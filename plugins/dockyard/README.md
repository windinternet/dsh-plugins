# @dsh-plugins/dockyard

## 概述

把"随手起了十几个开发服务"这件事变成**可观测、可解释、可收回**的托管。

它解决的具体问题：进程散落在多个终端里，谁在跑、跑的是什么说不清；日志随终端滚动消失；
端口冲突时不知道被谁占了；关掉终端等于杀掉服务，或者反过来服务活着但终端找不到了。

与既有进程管理器的区别是**不黑盒**：每个被识别出来的应用都带着判定理由，
每个状态变化都带着原因，拿不到确凿证据时如实标为"未知"而不是猜一个好看的值。
这一点对本仓库的用途尤其重要——智能体无法从黑盒里推理出发生了什么。

数据流向：**仅本机**。不发起任何出网请求；日志与状态只写在本机数据目录。

## 使用本包

### 安装

插件**没有任何依赖**，安装用 `file:` 或 registry spec：

```bash
dsh plugin --profile desktop add "file:/绝对路径/dsh-plugins/plugins/dockyard"
```

用 `link:` 会只建符号链接、不解析依赖树，插件启动时会以一行 `failed to import` 失败。

**不要把 `@deepseek-ai/*` 宿主包写进依赖。** 那会把它装进 profile 并遮住宿主自带的版本；
宿主一升级就触发精确版本校验失败，`tools` 行被禁用，整个启动挂掉。事故复盘见
[`docs/references/dsh-plugin-upgrade-failure.md`](../../docs/references/dsh-plugin-upgrade-failure.md)。

### 数据目录

状态文件与日志需要一个数据目录。默认按 `DSH_HOME` 推导为
`$DSH_HOME/plugin-data/dockyard`，`DSH_HOME` 不存在时退回 `~/.dsh-plugin-data/dockyard`。
建议在 profile 的 patch 里显式指定，避免跟随环境漂移：

```yaml
- id: dockyard
  config:
    dataDir: /Users/you/.dsh/plugin-data/dockyard
```

### 给智能体的工具

插件注册十三个工具，全部以 `dockyard_` 开头：

| 工具                | 作用                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| `dockyard_scan`     | 扫描目录，归一化成项目/生态/应用并给出判定理由。只读，不写入。                                          |
| `dockyard_add`      | 加入一个项目（项目下全部应用）到托管列表；会重新扫描以当前磁盘事实为准。 `candidateId` 可只加单个应用。 |
| `dockyard_status`   | 列出托管的服务与**真实**状态，以及 CPU/内存采样。                                                       |
| `dockyard_projects` | 按项目汇总应用数、运行中数量、CPU 与内存。                                                              |
| `dockyard_start`    | 启动服务。进程归本插件所有，客户端断开后仍然存活。                                                      |
| `dockyard_stop`     | 停止服务：温和终止 → 超时升级强杀 → 等进程真的消失才返回。                                              |
| `dockyard_restart`  | 停止后按原参数启动，改完代码/配置后重新加载用。                                                         |
| `dockyard_logs`     | 读取最近日志，`OUT` 为 stdout，`ERR` 为 stderr，`SYS` 为插件自身的事件。                                |
| `dockyard_metrics`  | 读取某个应用的 CPU/内存采样历史，或按项目汇总当前负载。                                                 |
| `dockyard_diagnose` | 调试组合视图：状态与原因 + 最近指标 + 最近 40 行日志。                                                  |
| `dockyard_external` | 发现 cwd 在项目根下、但不是 dockyard 启动的外部进程（pid/命令/CPU/内存/端口）。                         |
| `dockyard_takeover` | 接管项目下所有“外部启动”的应用：只终止匹配到的外部进程，再由 dockyard 启动，不启动其他应用。            |
| `dockyard_sync`     | 立即按磁盘事实同步已托管项目：新增应用、命令变化、失联/恢复。                                           |

典型用法是让智能体先 `dockyard_scan`，看判定理由是否合理，再 `dockyard_add` 托管项目；
排查问题用 `dockyard_diagnose` / `dockyard_metrics` / `dockyard_logs`。

### 周期同步（结构变化自动适应）

插件每 **5 分钟**（`syncIntervalMs`）对已托管项目做一次轻量重扫，也支持在服务页点「同步」手动触发：

- **新增应用**：项目重构后出现的新应用自动加入托管（状态为已停止，不自动启动）。
- **命令变化**：启动命令/参数变化会更新记录，旧参数压入 `commandHistory`；运行中的应用标记
  「需重启」，不会静默杀掉。
- **应用消失**：分支切换或删除后，旧记录标记「失联」，但记录、日志、指标历史全部保留；
  重新出现时自动恢复。
- **项目目录整体消失**：项目下应用标记失联，不会自动移除。

同步以磁盘上的项目事实为准，但**不自动重启、不删除旧设置**。这些是刻意的边界：自动重启
可能打断正在调试的进程，自动删除会丢掉日志与参数历史。

### 外部进程与非托管应用

如果服务是用户在终端里手动 `pnpm dev` / `npm run dev` 起的，dockyard 没有句柄。插件会：

- 枚举 cwd 在已托管项目下的外部服务进程，尽量匹配回具体应用；匹配依据是 cwd、
  应用目录/名称、`-pl`、`--filter` 等。无法唯一匹配的进程只展示为“未识别外部进程”。
- dockyard 自己启动的应用树（启动器及其子进程）不会被算作外部进程，避免同一个应用在托管/非托管之间跳动。
- 真正外部启动的应用在服务页显示「非托管」，可读状态、CPU/内存和监听端口；不能读日志。
- 非托管应用可以**停止**（只终止外部进程），也可以**重启**；重启就是手动接管：
  停止外部进程后由 dockyard 启动，从此日志、指标、启停都归插件管理。
- 接管入口只有三个：服务页顶部「一键接管」（全部非托管）、项目卡「一键接管」
  （本项目）、应用行「停止/重启/接管」（单个应用）。**没有自动接管，也不会自动启动
  项目里的其他应用。**
- 接管前的外部日志不可追溯（stdout 不在插件手里）；接管后日志才归插件管理。
- `dockyard_external` / `dockyard_takeover` 两个工具提供同样的能力给智能体。

### 进程独立性与日志

被 dockyard 启动的应用由独立启动器接管：应用不是 DSH 或插件的子进程，DSH 关闭后继续
运行。启动器把输出写入日志文件，按 `OUT` / `ERR` / `SYS` 标记来源并按大小轮转；
插件卸载默认不杀应用，保留运行态与启动器 pid，下次启动时重新接管。

### 快捷访问

运行中且监听了端口的应用会显示「访问」按钮，默认打开 `http://localhost:<端口>`；多端口可下拉
切换，选择会持久化为该应用偏好端口，下次访问直接使用。端口按启动器进程组聚合，访问本身
不会启动或停止应用。

### 保活与重试

- **不会自动启动未运行的应用。** 宿主启动、同步、扫描都不会拉起应用。
- 只有手动启动或手动接管后才进入守护；手动停止、移除、失联、关闭保活或重试次数用尽后停止。
- 退避延迟为 `min(退避上限, 退避基数 × 2^(n-1))`；稳定运行超过重置时间后重新计数。
- 服务页「保活设置」可调整开关、重试上限、退避基数/上限与稳定运行重置时间；保存策略本身
  不会启动或停止任何应用。宿主重启后会校验启动器 pid 并重新接管；无法确认时降级，不自动启动。

### 给智能体的技能

插件注册一个 `dockyard` 技能（`enableSkill: false` 可关闭），内容是“什么时候用 dockyard
调试本机服务、按什么顺序排查”。没有 `skills` 服务的组合会跳过注册并记一条警告，
工具本身照常可用。技能让调试类任务优先想到本插件，而不是随手 `npm run dev`。

### 界面

左侧栏会有一个**服务坞**入口（图标 + 名称），点击打开整页。页面是全局页面，不属于任何
Session，内部用五个 tab 区分功能：

| Tab       | 内容                                                                                                                                                                                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概览·指标 | 12 项指标（运行/异常/停止/需关注/项目/应用/语言/包管理器/CPU/内存/平均与最长运行）；状态、语言、包管理器、技术栈分布；CPU/RSS 趋势；宿主系统；项目负载与排行。                                                                                                         |
| 概览·健康 | 运行健康 hero；技术构成；资源趋势与宿主；紧凑版需要关注；项目负载与应用排行（CPU/内存切换）；正在运行的服务。                                                                                                                                                          |
| 服务      | 按项目分组的服务卡片：运行中应用显示托管/非托管徽标与「访问」入口，状态、语言/包管理器、命令、目录、CPU/内存、运行时长；非托管可停止/重启/接管（重启与接管等价）；支持搜索/状态/语言筛选，项目级批量启停与一键接管；顶部可打开保活设置，应用行展示守护状态与访问入口。 |
| 发现      | 点「扫描」打开系统文件夹选择框，选目录后自动扫描；结果按项目 / 生态 / 应用分组，逐项看理由并加入托管。                                                                                                                                                                 |
| 日志      | 选择服务与行数，轮询显示最近日志，标出日志来源（内存缓冲/日志文件尾部）。                                                                                                                                                                                              |

发现页只有一个「扫描」按钮：桌面端直接调用 Electron 的 `dialog.showOpenDialog`
（经 preload 暴露的 `__DSH_DIRECTORY_PICKER__.pick()`），选中目录后立即开始扫描；
普通 Web 端退回 `uiWorkspace.pickDirectory()`，由 Host 侧打开原生选择器。两者都不可用的
组合才展开“手动输入路径”作为兜底。

### 扫描规则

完整规则见 [`docs/design-docs/project-scanning.md`](../../docs/design-docs/project-scanning.md)。摘要：

- 扫描根自身是 git 仓库 → 一个项目，不展开；否则看直接子目录。
- 扫描根没有 git 时继续向子目录递归，直到发现 git；中间的非 git 文件夹是容器
  （`tian-gong-one` 这类目录本身不是项目，子仓库才是）。一旦发现 git 就停止递归，
  项目内部再嵌套的 `.git` 不再成为项目。无 git、无子项目、但有项目清单的目录标为
  “无 git”项目。
- 项目内按语言生态分组：Java-Maven、Java-Gradle、Node.js（pnpm/yarn/npm/bun）、
  PHP-Composer、Flutter、Go、Rust、Python、Shell；单生态不显示分组层。
- 只把能长期运行的服务入口算应用；library、构建脚本不算。每个应用都带判定理由。

托管模型：**托管的基本单位是项目，操作的最小单位是应用**。托管一个项目会把项目下
全部可运行应用一起加入列表；之后启停、重启、移除、查看日志都按应用进行。项目没有
可运行应用时不会出现在托管结果里。

输入框上方是一条与输入框等宽对齐的状态 bar：运行中/总数、异常与失联标签、项目数、
运行中应用的总 CPU/内存、语言 + 包管理器分组；可展开查看需要关注和正在运行的服务，
或跳转到整页。窄窗口先让生态块降级为「一组 + N」并补上已停止计数，更窄时再依次隐藏生态、规模和资源块，保留健康状态与操作。空状态、加载中
与状态接口不可用都有明确文案，而不是空白。

服务坞页头有「输入框状态条」开关：关闭后输入框上方不再渲染；选择由 Host 持久化在所有
会话间共享，刷新页面或重启宿主后保持。

面板数据来自三个同源、仅回环的路由：

| 路由                      | 方法 | 用途                                                        |
| ------------------------- | ---- | ----------------------------------------------------------- |
| `/plugin/dockyard/status` | GET  | 服务列表、扫描根目录、诊断。                                |
| `/plugin/dockyard/logs`   | GET  | 某个服务的最近日志（`id`、`lines`）。                       |
| `/plugin/dockyard/action` | POST | 启动/停止/重启/移除/扫描/加入；要求自定义头与 JSON 请求体。 |

三个路由都只接受本机来源（非回环地址直接 403），且不返回 CORS 头，因此跨站页面读不到
本机进程信息。写路由还要求 `x-dockyard-action: 1` 与 `application/json`：跨站 JS 设置
自定义头会触发预检，而这里不回应预检；HTML 表单也设不了这个头。不需要面板时可以设
`enablePanelRoute: false`，三条路由会一起关闭。

## 配置

配置写在 profile 的 `cordis.patch.yml` 里。插件刻意**不导出 schemastery 的 `Config`**，
因此宿主的插件设置页不会为它渲染字段表单；非法值会回退默认值并记诊断，而不是阻止启动。

| 字段                    | 默认值                                 | 含义                                         |
| ----------------------- | -------------------------------------- | -------------------------------------------- |
| `dataDir`               | 宿主工作目录下 `.dsh-plugins/dockyard` | 状态文件与日志的存放目录。                   |
| `gracefulTimeoutMs`     | `5000`                                 | 发温和终止信号后等待的上限，超时升级为强杀。 |
| `killTimeoutMs`         | `3000`                                 | 升级为强杀后等待进程消失的上限。             |
| `stopProcessesOnUnload` | `false`                                | 插件卸载时是否连带停止被托管的进程。         |
| `enablePanelRoute`      | `true`                                 | 是否注册面板所需的三个 HTTP 路由。           |
| `enableSkill`           | `true`                                 | 是否注册 `dockyard` 方法论技能。             |
| `syncIntervalMs`        | `300000`                               | 周期同步间隔（毫秒），0 表示关闭。           |
| `syncOnStart`           | `true`                                 | 插件启动后是否立即同步一次。                 |

## 理解实现

<details>
<summary>实现细节——点击展开</summary>

### 宿主重启后如何保持托管

状态文件里保存启动器 pid。宿主重启后 `init()` 会检查该 pid：

- 命令行仍含 `app-launcher.mjs` 且进程组号等于 pid：重新接管，状态保持 running；
- 进程已退出：降级为 crashed，并暂停守护，不自动启动；
- 进程存在但不是本插件启动器：降级为 unknown，不冒认。

这样既不会谎报，也不会把仍在运行的托管应用误判成非托管。

### 进程为什么归插件所有

子进程用 detached 方式启动，自成进程组。这样关掉终端或停掉调用方都不会顺手杀掉服务；
停止时也能对整组发信号，把服务自己拉起的子进程一起回收。

这里有一个踩过的坑：只有当子进程**确实自成一个进程组**时才用负 pid 发信号。
某些测试运行器会把子进程放在调用方同一个进程组里，此时对 `-pid` 发 SIGTERM
会把调用方自己所在的整组一起打掉。`plugin-kit` 里为此保留了 `ownsProcessGroup` 标记。

### 停止为什么是异步的

只发信号就返回，会让面板显示"已停止"而系统里还有残留进程，用户下次启动就撞端口。
所以停止是一个过程：发温和终止信号 → 轮询确认是否消失 → 超时升级为强杀 → 再确认。
两步都超时后不谎报成功，而是把状态标为异常退出并说明"状态不可信"。

### 日志

进程输出先进内存环形缓冲（面板读最近若干行），同时追加到文件（排查用完整记录）。
文件超过上限后轮转，避免长跑把磁盘写满。所有进入缓冲的文本都会先脱敏——
服务在启动日志里打印一次自己的配置（常常包含密钥）是极常见的做法。

### 不做的事

不引入 SQLite、不引入第三方进程库、不自己起守护进程。写入量很小，一个原子替换的
JSON 文件足够；DSH 宿主进程本身就是守护进程，而网关与面板由它提供。
每多一层就多一处可能不一致的状态。

</details>

## 模型体验

Agent 看到 `dockyard_*` 这六个工具的名称、描述与参数 schema。工具的渲染结果是人类可读的
文本行：状态行形如 `名字 [状态] 命令 目录 (pid) — 原因`，日志行形如 `[时间] OUT 内容`。

### Token 影响

装配时提供六个工具的声明；每次调用追加一行结果。`dockyard_logs` 的结果大小由 `lines`
参数控制（默认 100，上限 2000），因此不会因为一次日志读取就灌满上下文。

### KV Cache 影响

工具结果追加到对话中。本插件不注册系统提示词片段，也不改写请求消息，
因此不会让前缀缓存失效。

## 已知限制

- **只支持本机、单用户。** 不做远程访问、容器编排或集群。
- **外部进程发现依赖 `ps` 与 `lsof`。** macOS/Linux 支持；Windows 与缺少工具的环境只会显示
  “无法枚举”，不会误杀。接管前的外部日志不可追溯。
- **CPU/内存是进程组近似值。** 基于 `ps` 采样，CPU 可能超过 100%（多核），RSS 会重复计算
  共享页，属于上界估计；Windows 暂不采样，界面显示无数据。
- **宿主重启后依赖启动器 pid 重新接管。** 启动器被外部杀掉或 pid 被复用时无法认领，
  面板会降级为 crashed/unknown，而不是谎报运行中。
- **自动识别只覆盖声明式入口**（`package.json` 的 scripts、Python 入口文件、
  `scripts/` 或 `bin/` 下可执行脚本），不解析任意脚本内容。
- **视觉验证已完成（2026-10-21）。** 在一个临时 DSH profile 里真实安装并打开过：
  左侧栏入口、四个 tab、空状态、扫描/加入、启动/停止/移除、日志读取、停靠条跳转，
  以及浅色/深色主题都逐项看过。
- **工具名与注册已实测，但模型调用未实测。** 插件激活时成功注册了六个工具定义，
  没有用真实模型跑过一次完整调用。

## 失败行为

| 情况                           | 处理方式                                             |
| ------------------------------ | ---------------------------------------------------- |
| 状态文件损坏                   | 记一条诊断、重置为空状态，插件继续工作，不崩溃。     |
| 状态文件版本更高               | 忽略未知字段并提示，已识别的字段照常使用。           |
| 启动失败（命令不存在等）       | 状态置为异常退出并写明失败原因，不留下半死状态。     |
| 进程自行退出                   | 收到退出事件即更新状态与退出码，不永久停留在运行中。 |
| 停止后进程仍未消失             | 报告停止失败与"状态不可信"，不谎报成功。             |
| 面板路由不可用（无 HTTP 服务） | 记一条警告，面板显示不可用提示，Host 工具不受影响。  |
| 槽位注册失败                   | 记录警告，Host 半侧继续工作。                        |
| 写操作缺少自定义头或跨源       | 403，进程状态不变。                                  |
| 写请求体过大或不是合法 JSON    | 413/400，进程状态不变。                              |
