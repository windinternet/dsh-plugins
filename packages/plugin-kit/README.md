# @dsh-plugins/plugin-kit

写 DSH 插件用的共享底座。它只依赖 Node 内置模块，不依赖任何 DSH 内部包。

## 为什么存在

多个插件会重复遇到同一批问题：读一个不可信的配置文件、把密钥从日志里抹掉、
识别一个目录是不是可运行的应用、托管一个子进程、按需读日志尾部。
这些逻辑如果各写一遍，就会出现若干份行为不同的实现，而这种不一致没有任何检查能发现。

## 模块

| 导入路径                           | 内容                                         |
| ---------------------------------- | -------------------------------------------- |
| `@dsh-plugins/plugin-kit`          | 全部导出的汇总入口                           |
| `@dsh-plugins/plugin-kit/scan`     | 项目扫描：识别可运行应用并给出判定理由       |
| `@dsh-plugins/plugin-kit/process`  | 进程监管：启动、停止（含信号升级）、状态观测 |
| `@dsh-plugins/plugin-kit/log`      | 日志环形缓冲与按需读取尾部                   |
| `@dsh-plugins/plugin-kit/redact`   | 脱敏：密钥、URL 凭据、家目录路径             |
| `@dsh-plugins/plugin-kit/manifest` | 清单与边界解析工具                           |

## 设计约束

1. **只依赖 Node 内置模块。** 这个包被插件依赖，而插件在宿主进程内运行，
   多一个第三方依赖就多一份与宿主冲突的可能。
2. **纯 JS + JSDoc 类型。** 插件不做打包，共享库也不该引入构建步骤，
   否则"改完就能装"会变成一个需要构建的流程。
3. **纯函数优先。** 扫描、解析、脱敏都是纯函数，可以脱离宿主单独测试。
   有状态的部分（进程、缓冲）显式持有状态对象，并把清理责任写进接口。
