# 核心理念

这些理念决定了本仓库的取舍。当一条规则看起来多余时，先读这里——多数规则都能追溯到
下面某一条。理念本身变化时，要在这里改，而不是在别处打补丁。

## 1. 智能体的可读性优先

代码库首先要能被智能体**从仓库内**推理出来。任何运行期拿不到的东西等于不存在：散落在
聊天记录、个人笔记、口头约定里的知识，对智能体就是不存在的。

因此：

- 设计、规格、计划都提交进仓库，成为可检索、可 diff、可引用的事实源。
- 依赖与抽象倾向于"可完全内化"的选择。API 稳定的老技术往往比新潮方案更适合智能体。
- 遇到困难时的正确反应不是"再努力一点"，而是问：**缺了什么能力、文档或约束，
  以及怎么把它变成机械可执行的东西。**

## 2. 地图而非手册

给智能体一张地图，不是一本 1000 页的说明书。上下文是稀缺资源，一份庞杂的指令文件会
挤掉真正相关的信息，让智能体在错误的约束上做优化。

因此：`AGENTS.md` 保持简短并只做导航；细节放在 `docs/` 的对应文件里；采用渐进式披露，
从一个小而稳定的入口开始，再被指向下一步。

## 3. 强制不变量，而不是微观管理实现

在边界、正确性和可重复性上严格；在实现表达上给足自由。

因此：我们用注册表 + 校验脚本强制"插件必须有什么"（清单字段、patch 结构、文档存在），
但不规定插件内部怎么组织代码。判断标准是"资深工程师会不会觉得这过度复杂"，而不是
"是否用了某个库"。

## 4. 机械检查代替人的记忆

一条规则只要能被机械判定，就不该依赖人记得。文档链接、注册表一致性、密钥指纹都属于
这一类，全部编成了 `pnpm check` 里的检查项。

自定义检查的价值在于：它能**在错误信息里直接给出修复指令**，而通用 linter 只能报错。

## 5. 熵要持续清理，不要攒着一次性还

智能体会复现仓库中已有的模式，包括不理想的模式，因此漂移是必然的。技术债像高息贷款：
持续小额偿还远好于累积后痛苦地一次解决。

因此：已知问题写进 `docs/tech-debt-tracker.md`，明确延后而不是默默忽略；每个插件的
文档与规格在改动时同步更新，而不是等"以后补"。

## 6. 本机优先与隐私默认安全

本仓库是公开仓库，而插件面对的是用户的真实机器与真实代码。

因此：默认不把用户的工作区内容、会话、日志或遥测发到本机之外；密钥只从环境变量读取；
需要联网的能力必须显式声明数据流向；读取不可信数据必须在边界处解析并脱敏。

## 7. 短生命周期，低纠错成本

在智能体吞吐量远超人的注意力的环境里，等待的成本高于纠错的成本。

因此：改动直接在 `main` 上进行，不为一件事开一个分支；PR 保持短小；偶发失败重跑而不是
无限期阻塞。这不代表可以降低质量门槛——`pnpm check` 仍然必须通过。
