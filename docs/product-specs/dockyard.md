# dockyard 产品规格

## 一句话

在本机把"随手 `npm run dev` 起了一堆服务"这件事，变成**可观测、可解释、可收回**的托管。

## 问题

本机开发时同时跑十几个服务的现状是：

- 进程散落在多个终端窗口里，谁在跑、跑的是什么、占了多少资源，没人说得清。
- 日志随终端滚动消失，出问题时已经看不到现场。
- 端口冲突时不知道被谁占了。
- 重启机器后忘记哪些服务原本是开着的。
- 关掉终端等于杀掉服务，或者反过来，服务活着但找不到它的终端了。

现有的进程管理器（pm2 之类）解决了一部分，但它们是**黑盒**：配置格式自成一套、
状态不可读、出问题时只能猜。而这个仓库的用户是智能体与人协作——**黑盒是不可接受的**，
因为智能体无法从黑盒里推理出发生了什么。

## 目标（非目标同样重要）

**做：**

1. 扫描本机项目目录，识别出哪些是可运行的应用（而不是把所有目录都当应用）。
2. 受监管地启动、停止、重启应用；进程归插件所有，终端关掉不影响服务。
3. 日志落**文件**，可以按需读取和跟踪，而不是只活在终端缓冲区里。
4. 状态对人和智能体都可读：在跑什么、从哪个目录、什么命令、最近发生了什么。
5. 在 DSH 界面里有一个面板，能看状态、看日志、做启停。

**不做：**

1. 不做容器编排、不做集群、不做远程部署。这是本机工具。
2. 不替代 `npm run dev` 本身——它托管的正是这个命令。
3. 不引入自己的守护进程和 Web 服务器。DSH 宿主进程就是守护进程，
   DSH 的界面就是面板。多一层进程只会多一处不一致。
4. 不做自动发现以外的自动决策。识别不准时暴露给用户选，而不是猜。

## 数据流向

`local-only`。所有数据都留在本机：

- 不发起任何出网请求。
- 日志写在插件自己的数据目录下的文件里。
- 元数据（项目、应用、运行记录）写在本机存储里。
- 面板与 Host 之间的通信走 DSH 自己的宿主通道，不出本机。

## 用户可见行为

### 扫描

给定一个或多个根目录，扫描其中的项目并产出候选应用。判定依据是项目自身的声明
（例如 `package.json` 的 scripts、Python 的入口、Shell 脚本），而不是目录名猜测。

每个候选应用必须带上**判定理由**：依据哪个文件、哪一行、识别成什么类型。
理由是必需的，因为"为什么它认为这是应用"正是用户和智能体都需要的信息。

### 生命周期

- 启动：以应用的工作目录为 cwd 启动进程，采集 stdout 与 stderr 到日志文件。
- 停止：先发终止信号，超时后升级为强杀。**必须真的等进程结束**，不能发完信号就返回。
- 重启：停止后启动，且保持原有的启动参数。
- 状态：每个应用有一个明确的状态（未启动 / 启动中 / 运行中 / 已停止 / 异常退出），
  并记录最近一次状态变化的原因。

### 日志

- 每个应用一份日志文件，按需读取尾部若干行，并支持跟踪新增内容。
- 输出必须能区分 stdout 与 stderr。
- 日志文件有大小上限，超限后轮转，避免长跑把一个文件写到几 GB。

### 面板

在 DSH 界面中提供：

- 应用列表：名称、状态、工作目录、启动命令、运行时长。
- 单个应用的详情：最近日志、状态变化历史、可执行的启停操作。
- 空状态与错误状态有明确文案，不出现空白面板。

## 验收标准

以下每条都必须能实际演示，不接受"应该可以"：

| 编号 | 验收项                                 | 判定方式                                          |
| ---- | -------------------------------------- | ------------------------------------------------- |
| A1   | 插件能被 DSH 安装并激活                | 安装结果 `application` 为 `applied`，窗口内无报错 |
| A2   | 扫描能识别出仓库内的示例项目并给出理由 | 调用扫描能力，产出含判定理由的候选列表            |
| A3   | 启动一个长跑进程后状态变为运行中       | 启动后查询状态，进程 pid 与启动命令可读           |
| A4   | 关闭发起启动的客户端后服务仍然存活     | 启动后销毁调用方，再查询状态仍为运行中            |
| A5   | 停止能在超时内真正结束进程             | 停止后查询状态为已停止，且系统中该 pid 不存在     |
| A6   | 日志落文件且能按需读取                 | 读到本次运行产生的输出，stdout 与 stderr 可区分   |
| A7   | 面板能在 DSH 界面中打开并显示真实数据  | 打开面板看到应用列表与状态，明暗主题下都可读      |
| A8   | 面板在未安装/无数据时不崩              | 空状态下显示文案而非空白或报错                    |

## 已知限制（当前迭代）

- 只支持本机、单用户。多用户与远程访问不在范围内。
- 进程归属只在本进程存活期间有效：DSH 宿主进程重启后，之前托管的进程会失联，
  面板需要明确提示"失联"而不是谎报"正在运行"。
- 自动识别只覆盖声明式入口（package.json scripts 等），不解析任意脚本内容。
